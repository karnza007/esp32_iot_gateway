## 1. Idea

The advisor asked two questions about vendor FFT IP cores:

1. **Is the Gowin FFT core correct?**
2. **How easy is it to use** compared with Intel's FFT core (DE0-Nano, Cyclone IV, to be tested later)?

The method is the same for every device: the Mac generates a known test signal, the device
computes its FFT, and the Mac checks the answer against an exact reference.

The **ESP32-S3** was added as a third device. Espressif's ESP-DSP library has a 16-bit integer
FFT, so it answers two extra questions: *what does a software FFT on a microcontroller achieve?*
and *is an FPGA worth it for this job?*

Everything is done in **16-bit integer arithmetic**. Every device halves its data at each FFT
stage, so the output is `FFT(x) ÷ N` in int16. Python's floating-point FFT is used only as the
measuring ruler, not as a competitor.

# Part A — ESP32-S3 ✅

## 2A. Hypotheses

| | Hypothesis | Would be falsified by |
|---|---|---|
| **H3** | The ESP32's ESP-DSP 16-bit FFT is correct, and about as accurate as any other 16-bit FFT (same bit widths, same ÷2-per-stage scaling) | Any peak in the wrong bin, or RMS error above the correctness gate on any signal |
| **H4** *(ESP32 half)* | One 1024-point FFT takes a measurable, repeatable time on the ESP32, to be compared later with the FPGA | Timing that varies a lot from run to run |

## 3A. Test structure

```
  Mac (host/fft_bench.py)
   ├─ makes 8 test signals (int16)                       ┐
   ├─ sends them ──CH9102 USB-UART, 2 Mbaud──▶ ESP32-S3   │ checksum on request
   │                                 dsps_fft2r_sc16      │ and reply, so a transport
   │                                 + bit-reverse        │ error can't pass as an
   │                                 + CPU cycle counter  │ FFT error
   ◀────────────── spectrum + cycle counts ───────────────┘
   └─ scores it against: numpy.fft ÷ N (the ruler, float)
                         an ideal 16-bit integer FFT (the accuracy ceiling)
```

| Setting | Value |
|---|---|
| FFT sizes | 256, 512, 1024, 2048, 4096 |
| Arithmetic | int16 data, Q15 twiddles, ÷2 per stage |
| CPU clock | 240 MHz |
| Timing | Each FFT run 20× on fresh copies of the input; fastest run reported |
| Versions tested | **SIMD** (`dsps_fft2r_sc16_aes3`, assembly using the S3's vector instructions; what you get by default) and **plain C** (`dsps_fft2r_sc16_ansi`) |

**Test signals and what each one checks:**

| Signal | Checks |
|---|---|
| Impulse | Every bin, and the ÷N scaling (32767 in → 32 in every bin at N = 1024) |
| DC | All energy in bin 0 |
| Tone on a bin | One clean spike in the right bin |
| Tone between bins | Spectral leakage matches the reference |
| Two tones | Both found, correct relative size (12 dB apart) |
| Random noise (full scale) | Every butterfly exercised: the average error |
| Full-scale square wave | Largest real input: no overflow |
| Complex tone | The imaginary input path works |
| Overload *(not scored)* | Input too big for 16 bits: shows *how* the device fails |

**How "correct" is decided.** Two separate questions:

| Question | Rule |
|---|---|
| 1. Is it a correct FFT? | Every peak in the right bin, and RMS error ≤ **4 LSB** (see §6, problem 3) |
| 2. How accurate? | RMS error on random noise, compared with the best possible 16-bit FFT (0.43 LSB at N = 1024) |

*LSB = one step of the 16-bit integer, the smallest possible rounding error.*

**Prediction before the run:** a correct 16-bit FFT is off by about 0.4–1.3 LSB rms, depending
on how it rounds; a broken one is off by hundreds of LSB (measured on modelled designs, §6
problem 2).

## 4A. Results

**Correctness:** every peak in the right bin, at every size, for both versions.

| Version | Signals correct (4 LSB gate) |
|---|---|
| SIMD | **40 / 40** (8 signals × 5 sizes) |
| Plain C | **24 / 24** (8 signals × 3 sizes) |

**Accuracy (RMS error on random noise):**

| N | Best possible 16-bit | ESP32 plain C | ESP32 SIMD |
|---|---|---|---|
| 256 | 0.398 LSB | 0.488 | 1.763 |
| 1024 | 0.427 LSB | **0.455 (+0.5 dB)** | **1.821 (+12.6 dB)** |
| 4096 | 0.419 LSB | 0.426 | 1.837 |

Neither version gets less accurate as N grows.

**Speed (one FFT, 240 MHz):**

| N | SIMD FFT | Bit-reverse (to natural order) | **SIMD total** | Plain C FFT |
|---|---|---|---|---|
| 256 | 14.2 µs | 31 µs | 45 µs | 210 µs |
| 512 | 30.4 µs | 54 µs | 84 µs | — |
| **1024** | **65.1 µs** | **108 µs** | **173 µs** | **1,030 µs** |
| 2048 | 139 µs | 217 µs | 357 µs | — |
| 4096 | 297 µs | 439 µs | 736 µs | 4,868 µs |

Fastest and average of 20 runs differ by under 1 %. Two separate runs on two firmware builds
gave identical results.

**Predicted vs observed:**

| Quantity | Predicted | Observed |
|---|---|---|
| Error of a correct 16-bit FFT | 0.4–1.3 LSB | Plain C 0.43–0.49 ✅ · SIMD 1.76–2.00 ❌ (above the range) |
| Peaks in the right bin | all | all ✅ |
| Error grows with N | not expected | does not grow ✅ |

## 5A. Interpretation

**H3: partly confirmed.** Both versions are correct FFTs. The plain C version is about as
accurate as a 16-bit FFT can be. **The fast SIMD version is about 4× less accurate**, which is
more than predicted.

**Why the SIMD version is less accurate.** Three systematic effects, each exactly reproducible:

| Effect | Evidence | Which version |
|---|---|---|
| Output 1 LSB low | Impulse: every bin reads 31 instead of 32 | Both (rounding constant 0x7FFF instead of 0x8000 rounds exact halves down) |
| Gain loss of 2 LSB per stage | DC bin short by exactly 8, 12, 16, 20, 24 at N = 16, 64, 256, 1024, 4096 (= 2 × log₂N) | SIMD only |
| Extra rounding noise, mostly in the real part | 1.43 LSB left after removing bias and gain; real part 1.87, imaginary 1.10 | SIMD only |

Plain C doesn't have the last two, so they come from how the SIMD assembly does its arithmetic,
not from the FFT method. **ESP-DSP's fast version trades about 4× accuracy for 16× speed.** For
audio, the difference is inaudible: a 0.01 dB gain error and about 2 LSB of noise.

**Two surprises:**
- **Putting the output back in natural order takes longer than the FFT itself** (108 µs vs
  65 µs at N = 1024). The FPGA core outputs natural order directly, so the fair ESP32 number for
  comparison is the **total: 173 µs**.
- **The two versions fail differently when overloaded.** Plain C wraps around, matching the
  Python model to 0.1 LSB (1,448 vs 1,448 LSB rms). SIMD does about 7× less damage (212 LSB rms),
  which is consistent with saturating (clipping) instead of wrapping.

**H4 (ESP32 half): confirmed.** The timing is repeatable to under 1 %. The comparison with the
FPGA waits for Part B.

## 3B–5B. What happened so far

**The Tang Nano 4K cannot build a 1024-point Gowin FFT.** The core's working memory needs
**true dual-port** block RAM (both ports can read and write), because each FFT butterfly reads
two values and writes two values back in the same memory. The Tang Nano 4K's chip (GW1NSR-4C)
only offers single-port and semi-dual-port block RAM. Confirmed three ways:

1. **Gowin datasheet DS861, Table 2-5, note 1:** *"GW1NS-4C/4 do not support dual port mode."*
2. **Gowin IDE device lists:** the dual-port RAM generator supports the 9K and 20K chips but not the 4K's.
3. **Build test:** a minimal true dual-port RAM fails on the 4K and builds on the 9K and 20K (control).

Building the memory out of flip-flops instead limits the core to **16 points** (64 % of logic).

**The same 1024-point core builds on the Tang Nano 9K and 20K** (software build, no board
needed): 8 of 26 and 8 of 46 memory blocks, max clock 53.95 MHz and 88.3 MHz. **A 9K or 20K
has been requested from the advisor.** The test will run at the board's own **27 MHz** crystal,
with the FPGA↔ESP32 UART at **1 Mbaud** (27 MHz ÷ 27, exact).

**Ease-of-use evidence collected so far:**

| Observation | Why it matters |
|---|---|
| The IP generator offered block RAM for this exact chip, with no warning | The failure only showed up at the last build step (place & route) |
| The generator's own resource check said "6 BSRAM", which looked fine | It counts blocks but doesn't check that the chip has that block **type** |
| "Low Resource" and "High Performance" produced identical netlists | The option appears to do nothing for this configuration |
| The core is encrypted | The cause could only be found by trial builds |
| Generating the core in the GUI is instant once the options are set; retargeting to a new chip is: change the project's device, regenerate | Settings carry over unchanged (checked: same options, byte-identical twiddle tables, same 6 BSRAM / 2 DSP / 729 LUT / 184 ALU / 211 REG) |
| Synthesis of the vendor's own encrypted core gives 5 warnings (e.g. `'reconstructX' is already declared`, unconnected ports), all inside Gowin's `fft.v` | Harmless here, but a user can't tell that without trying it |

**F2: the data path to the 20K works (echo test, no FFT yet).** The FPGA stores the 1024-point
signal in block RAM and sends it back; the ESP32 relays it from and to the Mac.

```
 Mac ──2 Mbaud──▶ ESP32-S3 ──GPIO17 → pin 27, 1 Mbaud──▶ Tang Nano 20K: receive → RAM → send
 Mac ◀─────────── ESP32-S3 ◀──GPIO18 ← pin 28 ─────────────────────────────────┘
```

| Test | Result |
|---|---|
| 13 payloads (9 test signals + 4 raw byte patterns) × 50 frames | **650 / 650 frames back byte for byte, 0 byte errors** |
| Round trip ESP32 → FPGA → ESP32 | 82.4 ms (pure wire time 82.1 ms: no gaps) |
| Echo design resources | 318 logic (2 %), 2 of 46 BSRAM, Fmax 147.6 MHz vs 27 MHz needed |

So any error found in F3 belongs to the FFT core, not to the wires.

## 6. Problems and what they taught us

**1. The test tones flattered some designs.** The first version put tones on bins that scaled
with N. Tones on even-numbered bins scored 92 dB, while bin 37 scored 59 dB **in the same
correct model**. An even-bin tone divides so neatly through the butterflies that almost nothing
needs rounding, so the score reflected luck in the internal layout, not accuracy. **Fix:** all
tones on odd bins.

**2. The original pass rule would have failed correct designs.** The plan said "within 3 dB of
the ideal 16-bit FFT". To test the rule itself, other correct designs and deliberate bugs were
modelled:

| Design | RMS error |
|---|---|
| Best possible (rounds once per butterfly) | 0.43 LSB |
| Rounds twice per butterfly (common, correct) | 0.73 LSB, **failed the 3 dB rule** |
| Truncates instead of rounding (correct) | 1.32 LSB |
| Output in the wrong order (bug) | 575 LSB |
| Forgot to halve one stage (bug) | 417 LSB |
| Inverse instead of forward (bug) | 604 LSB |
| One bin missing (bug) | 7.1 LSB |

**Lesson:** "correct" and "how accurate" are two different questions. Correctness became a
pass/fail gate; accuracy became a number compared between devices. The self-test now re-proves,
on every run, that the gate passes every correct design and fails every bug.

**3. The gate had to move after the first real device.** The gate was first set at 2 LSB, based
on the modelled designs. The ESP32 SIMD version, which is correct, landed at 1.8–2.0 LSB and
crossed 2.0 once, by 0.003. The gate was raised to **4 LSB**: twice the worst real correct
result, still below the smallest bug (7.1 LSB). Because this was decided **after** seeing data,
both verdicts are kept in the record (2 LSB: 39/40; 4 LSB: 40/40). The Gowin core will be judged
by 4 LSB, which was fixed **before** it is tested.

**4. A web search claimed the Tang Nano 4K supports dual-port RAM.** The search summary repeated
the datasheet's family-wide headline ("Supports Dual Port mode") and missed the footnote that
excludes this exact chip. **Lesson:** check the primary source, and check the footnotes.
