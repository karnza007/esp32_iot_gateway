## 1. Idea

The advisor asked two questions about vendor FFT IP cores:

1. **Is the Gowin FFT core correct?**
2. **How easy is it to use** compared with Intel's FFT core (DE0-Nano, Cyclone IV, to be tested later)?

The method is the same for every device: the Mac generates a known test signal, the device
computes its FFT, and the Mac checks the answer against an exact reference.

The **ESP32-S3** was added as a third device. Espressif's ESP-DSP library has a 16-bit integer
FFT, so it answers two extra questions: *what does a software FFT on a microcontroller achieve?*
and *is an FPGA worth it for this job?*

Everything is done in **16-bit integer arithmetic**. Every device halves its data at each FFT
stage, so the output is `FFT(x) ÷ N` in int16. Python's floating-point FFT is used only as the
measuring ruler, not as a competitor.

# Part A — ESP32-S3 ✅

## 2A. Hypotheses

| | Hypothesis | Would be falsified by |
|---|---|---|
| **H3** | The ESP32's ESP-DSP 16-bit FFT is correct, and about as accurate as any other 16-bit FFT (same bit widths, same ÷2-per-stage scaling) | Any peak in the wrong bin, or RMS error above the correctness gate on any signal |
| **H4** *(ESP32 half)* | One 1024-point FFT takes a measurable, repeatable time on the ESP32, to be compared later with the FPGA | Timing that varies a lot from run to run |

## 3A. Test structure

```
  Mac (host/fft_bench.py)
   ├─ makes 8 test signals (int16)                       ┐
   ├─ sends them ──CH9102 USB-UART, 2 Mbaud──▶ ESP32-S3   │ checksum on request
   │                                 dsps_fft2r_sc16      │ and reply, so a transport
   │                                 + bit-reverse        │ error can't pass as an
   │                                 + CPU cycle counter  │ FFT error
   ◀────────────── spectrum + cycle counts ───────────────┘
   └─ scores it against: numpy.fft ÷ N (the ruler, float)
                         an ideal 16-bit integer FFT (the accuracy ceiling)
```

| Setting | Value |
|---|---|
| FFT sizes | 256, 512, 1024, 2048, 4096 |
| Arithmetic | int16 data, Q15 twiddles, ÷2 per stage |
| CPU clock | 240 MHz |
| Timing | Each FFT run 20× on fresh copies of the input; fastest run reported |
| Versions tested | **SIMD** (`dsps_fft2r_sc16_aes3`, assembly using the S3's vector instructions; what you get by default) and **plain C** (`dsps_fft2r_sc16_ansi`) |

**What "SIMD" and "plain C" mean.** Both are Espressif's own FFT from the same library
(ESP-DSP), computing the same 16-bit FFT. They differ only in *how* the CPU does the arithmetic:

| | Plain C (`_ansi`) | SIMD (`_aes3`) |
|---|---|---|
| Written in | Ordinary C, works on any ESP32 | Hand-written assembly for the ESP32-**S3** only |
| How it computes | One multiply or add per instruction | **S**ingle **I**nstruction, **M**ultiple **D**ata: the S3's vector unit works on 128-bit registers, i.e. **8 int16 numbers in one instruction** |
| Analogy | A cashier scanning items one at a time | A cashier scanning a whole tray of 8 items at once |
| Chosen by | Calling `dsps_fft2r_sc16_ansi()` explicitly | **Default:** `dsps_fft2r_sc16()` picks it automatically on an S3 |
| Speed, N = 1024 | 1,030 µs | 65 µs (**16× faster**) |
| Accuracy (noise) | 0.455 LSB (near the best possible 0.427) | 1.82 LSB (about 4× worse; see §5A) |

The SIMD version takes arithmetic shortcuts to fit 8 numbers through at once, and those
shortcuts round less carefully. Testing both shows the price of that speed.

**Test signals and what each one checks:**

| Signal | Checks |
|---|---|
| Impulse | Every bin, and the ÷N scaling (32767 in → 32 in every bin at N = 1024) |
| DC | All energy in bin 0 |
| Tone on a bin | One clean spike in the right bin |
| Tone between bins | Spectral leakage matches the reference |
| Two tones | Both found, correct relative size (12 dB apart) |
| Random noise (full scale) | Every butterfly exercised: the average error |
| Full-scale square wave | Largest real input: no overflow |
| Complex tone | The imaginary input path works |
| Overload *(not scored)* | Input too big for 16 bits: shows *how* the device fails |

**How "correct" is decided.** Two separate questions:

| Question | Rule |
|---|---|
| 1. Is it a correct FFT? | Every peak in the right bin, and RMS error ≤ **4 LSB** (see §6, problem 3) |
| 2. How accurate? | RMS error on random noise, compared with the best possible 16-bit FFT (0.43 LSB at N = 1024) |

*LSB = one step of the 16-bit integer, the smallest possible rounding error.*

**Prediction before the run:** a correct 16-bit FFT is off by about 0.4–1.3 LSB rms, depending
on how it rounds; a broken one is off by hundreds of LSB (measured on modelled designs, §6
problem 2).

## 5A. Interpretation

**H3: partly confirmed.** Both versions are correct FFTs. The plain C version is about as
accurate as a 16-bit FFT can be. **The fast SIMD version is about 4× less accurate**, which is
more than predicted.

**Why the SIMD version is less accurate.** Three systematic effects, each exactly reproducible:

| Effect | Evidence | Which version |
|---|---|---|
| Output 1 LSB low | Impulse: every bin reads 31 instead of 32 | Both (rounding constant 0x7FFF instead of 0x8000 rounds exact halves down) |
| Gain loss of 2 LSB per stage | DC bin short by exactly 8, 12, 16, 20, 24 at N = 16, 64, 256, 1024, 4096 (= 2 × log₂N) | SIMD only |
| Extra rounding noise, mostly in the real part | 1.43 LSB left after removing bias and gain; real part 1.87, imaginary 1.10 | SIMD only |

Plain C doesn't have the last two, so they come from how the SIMD assembly does its arithmetic,
not from the FFT method. **ESP-DSP's fast version trades about 4× accuracy for 16× speed.** For
audio, the difference is inaudible: a 0.01 dB gain error and about 2 LSB of noise.

**Two surprises:**
- **Putting the output back in natural order takes longer than the FFT itself** (108 µs vs
  65 µs at N = 1024). The FPGA core outputs natural order directly, so the fair ESP32 number for
  comparison is the **total: 184 µs** (copy + FFT + reorder; see §8).
- **The two versions fail differently when overloaded.** Plain C wraps around, matching the
  Python model to 0.1 LSB (1,448 vs 1,448 LSB rms). SIMD does about 7× less damage (212 LSB rms),
  which is consistent with saturating (clipping) instead of wrapping.

**H4 (ESP32 half): confirmed.** The timing is repeatable to under 1 %. The comparison with the
FPGA waits for Part B.

## 3B. What happened, step by step

### F1: the Tang Nano 4K cannot build a 1024-point Gowin FFT

The core's working memory needs **true dual-port** block RAM (both ports can read and write),
because each FFT butterfly reads two values and writes two values back in the same memory. The
Tang Nano 4K's chip (GW1NSR-4C) only offers single-port and semi-dual-port block RAM. Confirmed
three ways:

1. **Gowin datasheet DS861, Table 2-5, note 1:** *"GW1NS-4C/4 do not support dual port mode."*
2. **Gowin IDE device lists:** the dual-port RAM generator supports the 9K and 20K chips but not the 4K's.
3. **Build test:** a minimal true dual-port RAM fails on the 4K and builds on the 9K and 20K (control).

Building the memory out of flip-flops instead limits the core to **16 points** (64 % of logic).
The same 1024-point core builds on the 9K and 20K chips, so the advisor lent a **Tang Nano 20K**
(GW2AR-LV18QN88C8/I7). It runs on the board's own **27 MHz** crystal, no PLL.

### F2: the data path to the 20K works (echo test, no FFT)

```
 Mac ──2 Mbaud──▶ ESP32-S3 ──GPIO17 → pin 27, 1 Mbaud──▶ Tang Nano 20K: receive → RAM → send
 Mac ◀─────────── ESP32-S3 ◀──GPIO18 ← pin 28 ─────────────────────────────────┘
```

| Test | Result |
|---|---|
| 13 payloads (9 test signals + 4 raw byte patterns) × 50 frames | **650 / 650 frames back byte for byte, 0 byte errors** |
| Round trip ESP32 → FPGA → ESP32 | 82.4 ms (pure wire time 82.1 ms: no gaps) |

So any error found in F3 belongs to the FFT core, not to the wires.

### The FFT core's ports: what each pin of the block does

This is the block the IP Core Generator shows for `fft_1024`. Inputs are on the left, outputs on
the right. The names follow a convention: **x n** = time-domain sample number *n* (what goes in),
**X k** = frequency bin number *k* (what comes out); `re` / `im` = real / imaginary part;
`[15:0]` = 16 wires, i.e. a 16-bit number; `[9:0]` = 10 bits, i.e. 0 … 1023.

```
                 ┌──────────────────────────────┐
     clk ───────▶│                              │──▶ sod          ┐
     rst ───────▶│                              │──▶ ipd          │ input phase
   start ───────▶│                              │──▶ eod          ┘
                 │          fft_1024            │──▶ busy           compute phase
                 │   (Gowin FFT IP, 1024 pt)    │──▶ soud         ┐
xn_re[15:0] ════▶│                              │──▶ opd          │ output phase
xn_im[15:0] ════▶│                              │──▶ eoud         ┘
                 │                              │══▶ idx[9:0]       which sample / which bin
                 │                              │══▶ xk_re[15:0]  ┐ the result
                 │                              │══▶ xk_im[15:0]  ┘
                 └──────────────────────────────┘
        ─▶ one wire (a yes/no signal)      ═▶ a bus (a number)
```

**Inputs**

| Port | Width | What it does | How our design (`top.v`) drives it |
|---|---|---|---|
| `clk` | 1 | The clock. Everything inside happens on its rising edge | The board's 27 MHz crystal |
| `rst` | 1 | Reset, active high: puts the core back in its idle state | High for the first 128 clocks after power-up (power-on reset), then low |
| `start` | 1 | "Begin one FFT now." Only noticed while the core is idle | A one-clock pulse after the 1,024 samples have arrived over the UART |
| `xn_re[15:0]` | 16 | Real part of the input sample, signed (−32768 … 32767) | Read from our buffer: the sample the core asks for with `idx` |
| `xn_im[15:0]` | 16 | Imaginary part of the input sample, signed | Same buffer word (our test signals are complex; real audio would put 0 here) |

**Outputs: status signals (the core telling us what it is doing)**

| Port | Phase | High when… | How our design uses it |
|---|---|---|---|
| `sod` | input | **S**tart **o**f **d**ata: one clock, the core takes sample x(0) at the next edge | Time-split stamp: first sample |
| `ipd` | input | **I**n**p**ut **d**ata: for all 1,024 clocks in which the core takes a sample (one per clock) | While high, our buffer supplies sample `idx` (addressed one clock ahead, since the RAM answers one clock later) |
| `eod` | input | **E**nd **o**f **d**ata: one clock, with the last sample x(1023) | Time-split stamp: last sample |
| `busy` | compute | The core is calculating (the butterflies) | Time-split cross-check (5,140 cycles) |
| `soud` | output | **S**tart **o**f **u**nloa**d**: one clock, the first result is on `xk` | Time-split stamp: first result |
| `opd` | output | **O**ut**p**ut **d**ata valid: for all 1,024 clocks in which a result is on `xk` (one per clock) | While high, we write `xk` into the buffer at address `idx` |
| `eoud` | output | **E**nd **o**f **u**nloa**d**: one clock, with the last result | Stops the cycle counter; the frame engine then sends the buffer back |

**Outputs: data**

| Port | Width | What it carries |
|---|---|---|
| `idx[9:0]` | 10 | A number 0 … 1023. **While loading:** which sample the core is taking now. **While unloading:** which frequency bin is on `xk` now (in natural order 0, 1, 2, …, because "natural order" was chosen in the generator) |
| `xk_re[15:0]` | 16 | Real part of the result for bin `idx`, signed. Scaled to FFT(x) ÷ 1024 by the RS111 setting |
| `xk_im[15:0]` | 16 | Imaginary part of the result for bin `idx`, signed |

**One FFT, in order:** we pulse `start` → `sod`, then `ipd` for 1,024 clocks while we feed
`xn` (sample `idx` each clock) → `eod` → `busy` while it computes → `soud`, then `opd` for 1,024
clocks while we collect `xk` (bin `idx` each clock) → `eoud`. The timing diagram with real
clock counts is in §8.1. Source: Gowin IPUG503, Table 4-1 and Figure 6-1.

## 5B. Interpretation

**H1: partly confirmed.** For ordinary signals the Gowin core is a correct FFT, with peaks in the
right bins and errors of about 2 LSB: a little worse than the ESP32's SIMD version and about 5×
worse than plain C. Impulse and DC came out almost perfect (0.001 and 0.000 LSB).

**But the core breaks at full scale.** Inside the core, values are halved and rounded at each
of the 10 stages. The rounding leans slightly towards negative numbers. When a value stays near
−32768, the lowest number 16 bits can hold, through many stages, the rounding pushes it past the
edge and it **wraps around** to a large positive number, like a car odometer rolling over from
99999 to 00000. The core does not **saturate** (stop at the limit), so one wrapped value spoils
the whole spectrum. Both ESP32 versions handled the same signal correctly. *(The cause is
inferred from the measurements above; the core is encrypted, so its arithmetic can't be read.)*
**Practical rule: keep the Gowin core's input below about ±32,700, or leave one bit of headroom
(±16,384).** Gowin's manual doesn't mention this limit. What it means for the real microphone:
§9.

**H4: partly confirmed.** Counted in clock cycles, the FPGA is 6× more efficient than the fast
ESP32 version and 38× more than plain C. But the FPGA clock (27 MHz) is 9× slower than the
ESP32's (240 MHz), so **in time** the ESP32 SIMD version still finishes first (184 vs 266 µs).
The FPGA's real advantage here is that it uses **no CPU**: the ESP32 can do other work while the
FPGA computes.

| Generating the core is instant; retargeting to a new chip = change the project's device, regenerate | Settings carried over unchanged (checked) |

| The IDE ships only a one-page help; the real manual (IPUG503) is on Gowin's website, and the first link tried was broken (403) | Found via the FFT product page |
| The manual's text is vague ("after several cycles…"); only the timing diagram (Figure 6-1) is exact | The core worked first time when driven exactly as the diagram shows |

## 6. Problems and what they taught us

**1. The test tones flattered some designs.** The first version put tones on bins that scaled
with N. Tones on even-numbered bins scored 92 dB, while bin 37 scored 59 dB **in the same
correct model**. An even-bin tone divides so neatly through the butterflies that almost nothing
needs rounding, so the score reflected luck in the internal layout, not accuracy. **Fix:** all
tones on odd bins.

**2. The original pass rule would have failed correct designs.** The plan said "within 3 dB of
the ideal 16-bit FFT". To test the rule itself, other correct designs and deliberate bugs were
modelled:

| Design | RMS error |
|---|---|
| Best possible (rounds once per butterfly) | 0.43 LSB |
| Rounds twice per butterfly (common, correct) | 0.73 LSB, **failed the 3 dB rule** |
| Truncates instead of rounding (correct) | 1.32 LSB |
| Output in the wrong order (bug) | 575 LSB |
| Forgot to halve one stage (bug) | 417 LSB |
| Inverse instead of forward (bug) | 604 LSB |
| One bin missing (bug) | 7.1 LSB |

**Lesson:** "correct" and "how accurate" are two different questions. Correctness became a
pass/fail gate; accuracy became a number compared between devices. The self-test now re-proves,
on every run, that the gate passes every correct design and fails every bug.

**3. The gate had to move after the first real device.** The gate was first set at 2 LSB, based
on the modelled designs. The ESP32 SIMD version, which is correct, landed at 1.8–2.0 LSB and
crossed 2.0 once, by 0.003. The gate was raised to **4 LSB**: twice the worst real correct
result, still below the smallest bug (7.1 LSB). Because this was decided **after** seeing data,
both verdicts are kept in the record (2 LSB: 39/40; 4 LSB: 40/40). The Gowin core will be judged
by 4 LSB, which was fixed **before** it is tested.

**4. A web search claimed the Tang Nano 4K supports dual-port RAM.** The search summary repeated
the datasheet's family-wide headline ("Supports Dual Port mode") and missed the footnote that
excludes this exact chip. **Lesson:** check the primary source, and check the footnotes.

## 8. How the time was measured (the time split)

**Why split the time?** "266 µs" or "184 µs" alone doesn't say *where* the time goes. Each
device's FFT is really a few steps in a row, so each step is timed separately. That shows which
step dominates, and lets the devices be compared step for step.

**The tool for both devices is a cycle counter**: a counter that adds 1 on every clock tick.
Read it before and after a step; the difference is how many clock cycles the step took.
Dividing by the clock frequency gives the time: cycles ÷ MHz = µs.

### 8.1 FPGA: four phases, marked by the core's own signals

The Gowin core announces each phase on its output wires (Gowin manual IPUG503, Figure 6-1).
The FPGA design (`fpga_fft/src/top.v`) runs one counter from the moment it pulses `start`, and
**writes down the counter's value** the first time each signal goes high:

```
counter   0  1                1024 1025              6165 6166               7189
start     ▔▔____________________________________________________________________
sod       ___▔▔_________________________________________________________________  first sample
ipd       ___▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔______________________________________________  taking samples (1 per clock)
eod       ______________________▔▔______________________________________________  last sample
busy      _________________________▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔_______________________  computing
soud      ________________________________________________▔▔____________________  first result
opd       ________________________________________________▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔_  results out (1 per clock)
eoud      ___________________________________________________________________▔▔_  last result
phase        ◀─────load 1,024────▶ ◀───compute 5,141────▶ ◀────unload 1,024───▶
```

| Phase | What happens | From → to | Formula | Cycles | Time (27 MHz) | Share |
|---|---|---|---|---|---|---|
| 1 Setup | Core reacts to `start` (counter 0, before the first sample) | `start` → before `sod` | sod | 1 | 0.04 µs | 0 % |
| 2 Load | Core takes the 1,024 samples, **one per clock** | `sod` → `eod` | eod − sod + 1 | **1,024** | 37.9 µs | 14.2 % |
| 3 Compute | 10 stages of butterflies | after `eod` → before `soud` | soud − eod − 1 | **5,141** | 190.4 µs | 71.5 % |
| 4 Unload | Core hands out the 1,024 results in natural order, **one per clock** | `soud` → `eoud` | total − soud | **1,024** | 37.9 µs | 14.2 % |
| **Total** | | `start` → last result | | **7,190** | **266.3 µs** | |

The four phases add up to the total exactly, by construction. As a cross-check, the core's
`busy` signal is high for 5,140 cycles (from 1,025 to 6,165), which matches the compute phase.
All 9 test signals gave exactly the same numbers: the core's timing doesn't depend on the data.

**What the numbers mean:**
- A 1024-point FFT has 10 stages × 512 butterflies = **5,120 butterflies**. The compute phase
  takes 5,141 cycles, so the core does **one butterfly per clock**, plus about 21 cycles to fill
  its pipeline. Its 2 DSP multipliers do one complex multiply per clock.
- Loading and unloading are fixed at one sample per clock: 2,048 of the 7,190 cycles (28 %) are
  just moving data in and out.
- The time is set by the clock: at 27 MHz each cycle is 37 ns. The same design would be ~3×
  faster with a faster clock (it passes timing up to 80–94 MHz), but that needs a PLL; not tested.
- For audio: at the INMP441's top rate (46.875 kHz), 1,024 new samples arrive every 21.8 ms.
  One FFT takes 0.27 ms, so the core would be busy about **1.2 %** of the time.

**Cost of measuring:** the stamp counters add 186 logic cells and 169 registers to the design
(1,426 → 1,612 logic, 480 → 649 registers). They only watch the core; the FFT results are
identical to the build without them.

### 8.2 ESP32-S3: three steps, timed with the CPU cycle counter

The CPU has a built-in cycle counter (`esp_cpu_get_cycle_count()`, 240 per µs). The firmware
(`firmware/fft_bench`) reads it between the steps of one run:

```
 c0 ──[ 1 copy input ]── c1 ──[ 2 FFT butterflies ]── c2 ──[ 3 bit-reverse ]── c3
       memcpy 4,096 bytes      10 stages, in place          reorder to natural order
```

| Step | What happens | Why it's needed |
|---|---|---|
| 1 Copy input | Copy the 1,024 samples into the work buffer | The FFT overwrites its input ("in place"), so every run needs a fresh copy. This matches the FPGA's *load* phase |
| 2 FFT | The 10 stages of butterflies (SIMD or plain C) | The actual computation. Matches the FPGA's *compute* phase |
| 3 Bit-reverse | Swap results into natural order (bin 0, 1, 2, …) | ESP-DSP leaves results in "bit-reversed" order (bin 0, 512, 256, 768, …). The FPGA hands out natural order directly, so the ESP32 needs this step to produce the same answer. Matches the FPGA's *unload* phase |

**How it's made reliable:** each run is repeated **20 times**, and the **fastest** time of each
step is reported. A slower run means an interrupt (e.g. USB or Wi-Fi housekeeping) paused the
CPU in the middle; the fastest run is the one nothing interrupted. As a cross-check, the whole
run (c0 → c3) is also timed in one piece: it equals the sum of the three steps within 0.1 %.

**Results, N = 1024 (240 MHz):**

| Step | SIMD cycles | SIMD time | Share | Plain C cycles | Plain C time | Share |
|---|---|---|---|---|---|---|
| 1 Copy input | 2,596 | 10.8 µs | 5.9 % | 2,596 | 10.8 µs | 0.9 % |
| 2 FFT | 15,631 | 65.1 µs | 35.4 % | 247,166 | 1,029.9 µs | 89.6 % |
| 3 Bit-reverse | 25,972 | **108.2 µs** | **58.8 %** | 25,972 | 108.2 µs | 9.4 % |
| **Total** | **44,199** | **184.2 µs** | | **275,734** | **1,148.9 µs** | |

**What the numbers mean:**
- **SIMD:** 15,631 cycles ÷ 5,120 butterflies = about **3 cycles per butterfly**, thanks to 8
  numbers per instruction. The FFT is so fast that **reordering the output takes longer than
  computing it**. The reorder used here is ESP-DSP's plain-C version: its fast one isn't
  available for this data type on the S3.
- **Plain C:** about **48 cycles per butterfly**; the FFT is 90 % of the time.
- Copy and bit-reverse are identical in both versions (same code); only step 2 differs.

### 8.3 Step-by-step comparison (N = 1024)

| Matching step | Gowin FPGA (27 MHz) | ESP32 SIMD (240 MHz) | ESP32 plain C (240 MHz) |
|---|---|---|---|
| Get the input in | load: 1,024 cyc = 37.9 µs | copy: 2,596 cyc = 10.8 µs | copy: 2,596 cyc = 10.8 µs |
| **Compute the FFT** | **5,141 cyc = 190.4 µs** | **15,631 cyc = 65.1 µs** | **247,166 cyc = 1,029.9 µs** |
| Results in natural order | unload: 1,024 cyc = 37.9 µs | bit-reverse: 25,972 cyc = 108.2 µs | bit-reverse: 25,972 cyc = 108.2 µs |
| **Total** | **7,190 cyc = 266.3 µs** | **44,199 cyc = 184.2 µs** | **275,734 cyc = 1,148.9 µs** |
| Cycles per butterfly | **~1** | ~3 | ~48 |

**In one sentence:** the FPGA does the most work per clock tick (one butterfly per cycle, and
the reorder comes for free), but its clock is 9× slower, so the ESP32's SIMD version still
finishes first, while the FPGA leaves the CPU completely free.

**To reproduce:**

```bash
fpga_fft/build.sh program                     # FPGA design with phase stamps
python host/fft_bench.py fpga                 # FPGA: correctness + time split
python host/fft_bench.py esp32                # ESP32 SIMD: correctness + time split
python host/fft_bench.py esp32 --impl ansi    # ESP32 plain C
```

## 9. Microphone input levels: can the real microphone hit the FFT's limit?

The Gowin core fails only when its input is within a hair of full scale (§4B). The audio project
feeds it from an INMP441 microphone, so the question is: **how big are the numbers the
microphone actually produces?**

### 9.1 Two different "rulers" for loudness

| Ruler | Measures | Where 0 is |
|---|---|---|
| **dB SPL** (sound pressure level) | How loud a sound is **in the air** | 0 = the quietest sound a human can hear |
| **dBFS** (decibels relative to full scale) | How big the **number** coming out of the microphone is | 0 = the **biggest number possible**; everything else is negative ("below full") |

Think of the microphone's output as a **glass of water**. Full scale is the glass filled to the
top: in our 16-bit samples, the number **32,767**. 0 dBFS = full, −6 dBFS ≈ half full,
−20 dBFS = one tenth full.

### 9.2 The datasheet links the two rulers

The INMP441 datasheet gives one calibration point:

> **Sensitivity: a 94 dB SPL tone at 1 kHz gives −26 dBFS** (min −29, typ −26, max −23).
> "0 dBFS" means a sine whose **peak** just touches full scale.

The datasheet's own example: 94 dB SPL gives a 24-bit peak of 420,426. Our FPGA keeps the top 16
of the 24 bits (divide by 256), so **94 dB SPL → peak 1,642** in our samples (5 % of full scale).

| Other datasheet values | |
|---|---|
| Maximum acoustic input | 120 dB SPL |
| Noise floor | −87 dBFS (≈ 1.5 in our 16-bit samples) |
| Dynamic range | 87 dB |
| Output | 24-bit, two's complement |

### 9.3 One rule to move up or down

- **+6 dB ≈ ×2** (twice as big a number), **+20 dB = ×10**.
- Starting from 94 dB → 1,642, every other level follows. Formula: peak = 32,767 × 10^((SPL − 120) / 20).

```
 sound level      sample peak      how full the "glass" is
   120 dB   ──▶   32,767   ████████████████████  100 %  ← full: the microphone's maximum
   114 dB   ──▶   16,400   ██████████             50 %
   100 dB   ──▶    3,300   ██                     10 %  shouting right at the microphone
    94 dB   ──▶    1,642   █                       5 %  ← the datasheet's calibration point
    80 dB   ──▶      330                           1 %  loud voice, close
    60 dB   ──▶       33                         0.1 %  normal conversation
    40 dB   ──▶        3                        0.01 %  quiet room
```

*(Sound examples are typical values, for orientation.)* The key fact: 120 − 94 = 26 dB, which
exactly cancels the −26 dBFS sensitivity, so **the microphone reaches full scale at 120 dB SPL**,
its own maximum and about the loudest sound a human ear can stand. Microphones vary by ±3 dB: a
"hot" unit (−23 dBFS) is full at 117 dB SPL.

### 9.4 What it means for the FPGA

| | Sample value | Sound level |
|---|---|---|
| Gowin core starts failing | above ±32,748 | ≈ 120 dB SPL (the glass completely full) |
| Loudest normal sound (shouting right at the microphone) | ~3,300 | ~100 dB SPL |
| Normal conversation | ~33 | ~60 dB SPL |

- **In normal use the FFT never gets near its limit.** Normal sounds use 10 % or less of the
  range, about 20 dB (10×) below the failure zone.
- **Only an overloaded microphone can reach it**: tapping or knocking on it, blowing into it, or a
  very loud bang right next to it. Then the Gowin FFT would output garbage instead of a clipped
  but sensible spectrum.
- **Cheap insurance (open decision):** clamp the FFT's input to ±32,700 in the FPGA. It changes
  nothing below about 119.98 dB SPL (where the microphone already distorts), costs only a few
  logic cells, and makes the failure impossible.

## 10. Simulating the Gowin core with free tools

### 10.1 What simulation is, and why it matters here

**Simulation** runs the hardware design **on the computer instead of on the FPGA**. A
*testbench* (a small Verilog program) feeds the design inputs, here our test signals, and every
internal wire can be watched on every clock tick. On the board we only see what comes out; in
simulation we can see *inside*, for example where the full-scale signal goes wrong.

### 10.2 Why Gowin's own tools can't do it

| Reason | Detail |
|---|---|
| **Gowin's IDE has no simulator** | Its tools are synthesis, place & route, the programmer, the floorplanner and an on-chip logic analyser (GAO, which needs the board). There is no program for running a design on the computer. Gowin ships *simulation libraries* (`IDE/simlib/`) meant for other companies' simulators |
| **Those simulators are commercial** | Professional simulators (e.g. ModelSim/Questa) are paid products, and not made for macOS |
| **The core's main file is encrypted** | `fft_1024.v` is protected with the standard Verilog encryption (15 `protect` blocks). Only a tool holding Gowin's key can read it: Gowin's own synthesizer, or a commercial simulator Gowin has given the key to. **Free simulators cannot read it** |

### 10.3 What was used before, and what is used now

| | Before: the audio design (M1–M3) | Now: the Gowin FFT core |
|---|---|---|
| Simulator | **Icarus Verilog** (free, open source) + `vvp` | **Icarus Verilog** (the same) |
| What was simulated | Our **own** Verilog: `sample_gen`, `framer`, the whole I2S → UART chain, with a microphone model | Gowin's FFT core, using its **gate-level model** `fft_1024.vo` |
| Testbenches | `fpga/sim/tb_gen.v`, `tb_framer.v`, `tb_chain.v` (run with `fpga/sim/run_sims.sh`) | `fpga_fft/sim/tb_fft.v` (run with `python host/fft_bench.py sim`) |
| Why it was possible | All the code was ours and readable | The `.vo` file is **not encrypted**, and Gowin's primitive library is readable too |

### 10.4 How it works

The IP generator writes two versions of the core:

| File | What it is | Encrypted? | Used for |
|---|---|---|---|
| `fft_1024.v` | The core for Gowin's synthesizer | **Yes** | Building the FPGA design |
| `fft_1024.vo` | "Post-PnR Verilog Simulation Model": the finished core as ~1,100 chip building blocks wired together (342 LUT3, 207 LUT2, 174 LUT4, 184 ALU, 211 flip-flops, 4 DPB, 2 pROM, 2 MULTADDALU18X18) | **No** | Simulation |

The `.vo` only says "a LUT4 here, a dual-port RAM there". How each block *behaves* is described
in Gowin's library `prim_sim.v` (16,770 lines, also unencrypted). Together:

```
 tb_fft.v (our testbench) + fft_1024.vo (the core, gate by gate) + prim_sim.v (how each gate behaves)
        └────────────────────────────── iverilog ──────────────────────────────┘
                                          │
                                     vvp (runs it)  ──▶  1,024 results + phase stamps
```

The testbench drives the core exactly as Gowin's manual describes (while `ipd` is high, supply
sample `idx`), independently of our FPGA design `top.v`, and writes down the same phase stamps
the board measures.

**Three things had to be solved** (worth knowing for anyone repeating this):

1. **Gowin's flip-flops look for a chip-wide "global set/reset" block called `GSR`.** On the chip
   it exists automatically; in simulation the testbench must contain one: `GSR GSR(.GSRI(1'b1));`.
2. **Icarus must be told which module is the top** (`-s tb_fft`). Otherwise it tries to build
   every unused block in the library on its own, and those fail.
3. **A race in the first testbench:** `start` changed on the same clock edge on which it was
   read, so the bookkeeping missed it. Fixed by changing inputs just after the rising edge, as a
   real flip-flop would.

### 10.5 Result: the simulation behaves exactly like the board

| | Board (Tang Nano 20K) | Simulation (Icarus) |
|---|---|---|
| Phase stamps sod / eod / busy↑ / busy↓ / soud / last result | 1 / 1024 / 1025 / 6165 / 6166 / 7189 | **1 / 1024 / 1025 / 6165 / 6166 / 7189** |
| Total cycles | 7,190 | **7,190** |
| RMS error, all 9 signals | e.g. noise 2.1835, tone 2.3299, full scale 1023.778 | **identical on all 9, to 4 decimals** (incl. max error) |
| Full-scale signal | WRONG | **WRONG, in exactly the same way** |
| Time per FFT | 266 µs | ~2.5 s of computer time |

Matching rms *and* max error on all 9 signals is very strong evidence that the outputs are
identical. A bin-by-bin, bit-for-bit comparison (`fft_bench.py sim --board`) is ready, but
couldn't run on 2026-10-09: the ESP32 ↔ FPGA link stopped responding overnight (to be
checked: wiring).

**What this means:**
- **For the ease-of-use comparison:** the Gowin core **can** be simulated with free tools, even
  though its main file is encrypted. But Gowin doesn't document this path, and it needed the
  three fixes above.
- **For this project:** changes can be tried in seconds without the board, and the full-scale
  failure can now be traced *inside* the core, to confirm the cause that §5B could only infer.

```bash
python host/fft_bench.py sim            # simulate all test signals, score them
python host/fft_bench.py sim --board    # ... and compare every output bit with the real FPGA
```
