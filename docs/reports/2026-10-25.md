## 1. Idea

H1 (test pattern) and H2 (spectrum of a test tone) worked on 2026-10-09. H3 needs real sound:
the INMP441 microphone wired to the 20K. On 10-09 the mic gave no data, and its connection was
unstable even on the ESP32. The question this week: **where does the mic signal go wrong
between the microphone and the FFT, and how do we get a clean signal into the 20K?**

## 2. Hypothesis

> **H1.** *If the INMP441 is clocked by the 20K and its samples are sent to the PC through the
> existing UART link, the viewer shows the same clean audio as the ESP32 does, because the
> receiver logic passes simulation against a mic model.*
> **Falsified by:** scrambled samples while the test tone through the same link stays clean.

> **H2.** *If the same mic and the same receiver logic work on a different board (the Tang
> Nano 4K), the fault is specific to the 20K setup (pins, wiring, clock).*
> **Falsified by:** the 4K showing the same scrambled data.

## 3. Test structure

The HDMI chain hides the samples, so a separate **mic check** build was made first:

```
  INMP441 ══ THE VARIABLE: board, pins, bit clock ══▶ FPGA (i2s_master_rx) ──▶ framer ──▶ UART 1 Mbaud
                                                       ▲ S1: 1 kHz test tone          │
                                                                                      ▼
                         inmp441_viewer.py / sd_raw.py ◀── USB ◀── ESP32-S3 fpga_uart_bridge
```

| Part | What it does |
|---|---|
| `fpga_fft/src/top_mic_uart.v` | 20K, 27 MHz crystal, no PLL. Samples go out in the audio project's v3 frames, so the existing viewer reads them |
| Test tone (S1) | A 1 kHz tone made inside the FPGA. If it arrives clean, the link is proven and any fault is before the FPGA |
| Raw-bits mode (S2) | Sends all 64 bits of every WS frame from the SD wire, exactly where the receiver samples them. `host/sd_raw.py` shows where in the frame the mic is talking |
| Swap test | The same mic and the same `i2s_master_rx.v` on the Tang Nano 4K (`fpga/src/top.v`) |

**Prediction for a working mic in a quiet room:** values near zero, neighbouring samples
strongly alike (correlation well above 0.5), no repeated odd values. A word shifted by one
bit shows up as values like −64, −128 or 32767 and a correlation near 0.

## 5. Interpretation

- **H1 was falsified** on pins 73–76: the test tone was clean but the mic data was not, so the
  fault was between the mic and the FPGA's receiver.
- **H2 held**: the 4K, with the same mic and the same receiver file, was clean in its first
  run. That cleared the microphone and the logic in one step.
- On the 20K, the run that worked changed **two things at once**: the pins (76/74/75 →
  25/26/29) and the bit clock (643 kHz → 964 kHz, the 4K's value). Which one mattered is
  **not known**. 643 kHz is close to the mic's 0.5 MHz minimum, but 2.25 MHz also failed on
  pin 76, so the bit clock alone doesn't explain it. The demo keeps both settings.
- Raw bits (run 7) showed the mic talking in the half of the frame where a left-channel mic
  must be silent. So the mic was not following the WS signal the FPGA sent, which fits a
  disturbed clock or WS at the mic rather than a logic fault.

## 6. Problems and what they taught us

| Problem | What it taught us |
|---|---|
| **A scope probe on SCK alone broke a working mic** (run 2). The first conclusion was that the mic was faulty; the same result on a second mic, and moving the probe to one wire at a time, pointed to the probe | A probe adds capacitance and a long ground lead. On a fast clock edge this can create extra edges the mic counts. Probe SD and WS, not SCK, and check a "broken part" conclusion against a second part |
| **Glitch theory:** SCK/WS were decoded from a counter by logic, which can flick briefly when several counter bits change together. Fixed by driving them straight from flip-flops | A real fault, but it changed nothing on the board. Kept as good practice; said so instead of claiming it as the fix |
| **WS race:** WS changed on the same SCK edge the mic reads it on, so the mic could see the old or the new value. Fixed: WS now changes on the falling edge; capture start `CAP_START` 2 → 1 | Also real, also not the cause. The simulation mic models were rewritten to read WS on the rising edge and change SD on the falling edge like the real chip, so this kind of race now shows up in simulation |
| A week of single changes on the 20K (pin, drive, clock, logic) without isolating the cause | **Swap in a known-good reference early.** The 4K test took one run |
| Arduino's `ctags` stopped working after macOS 27 ("bad CPU type") | It's an Intel binary; installing Rosetta fixed it |
| Raw-bits mode needs 4 words per sample: it fits the 1 Mbaud link only at `BCLK_DIV` ≥ 42 | Documented in `top_mic_uart.v`; at today's 28 it would need 120 kB/s of a 100 kB/s link |

**Simulation status:** `tb_mic_uart` (mic + tone, `BCLK_DIV` 28), `tb_h3_mic` (8 gains, 77
clocks per SCK) and `fpga/sim/run_sims.sh` (audio project, shared receiver) all pass.
