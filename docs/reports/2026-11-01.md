## 2. Hypothesis

> **H1.** *If the benchmark is removed from the HDMI build, logic falls by about 1,300 and block
> RAMs by 8, because the synthesis report lists `u_link` (the benchmark, with its own 1024-point
> FFT) at 1,319 LUTs, 622 registers and 8 block RAMs, and nothing else depends on it.*

It would be wrong if the drop were much smaller (the tool shares or keeps logic), or if the
picture, buttons or LEDs stopped working (something did depend on it).

> **H2.** *Timing gets no worse,* since the 27 MHz benchmark and the 74.25 MHz demo share no logic.
> A smaller design usually places more easily, but this is not guaranteed.

## 5. Interpretation

- **H1 holds.** Registers, block RAMs and pins fell by exactly the benchmark's share. Logic fell
  **more** than predicted (−1,496 vs ≈ −1,300): the estimate counted only the benchmark's LUTs
  (1,319) and forgot its 221 adders (ALU). 1,319 + 221 = 1,540, within 3 % of what was saved.
- **The demo alone uses about one eighth of the chip.** The **FFT is the biggest part** (about
  45 % of the demo's logic and 9 of its 12 block RAMs). Text is second (about 20 %), and most of
  that is the text table, built from logic. Everything else is small.
- **H2 holds, better than expected.** The demo's clock reaches 83.3 MHz, 12 % above the 74.25
  needed. The slowest path moved: it was our text-table lookup (`rom_text`); it is now inside the
  Gowin FFT core (a multiplier output into its memory). Timing varies a little from build to build
  with placement, so 83.3 is one build, not a guarantee. The point is that the margin went from
  0.8 % to 12 %.
- **Room for the next steps:** 88 % of the logic and 34 of 46 block RAMs are free. A lower sample
  rate, a noise floor and a debug UART (§7) will all fit easily.

## 8. Sample rate ÷2: 44,621 → 22,311 Hz (2026-10-29)

**Why:** the sounds we test with (voice, 220/440 Hz, instruments) sit well under 11 kHz. Half the
sample rate puts all 512 bars on 0–11.2 kHz, so each bar covers half as many Hz.

| | ÷26 (before) | **÷52 (now)** |
|---|---|---|
| Mic bit clock (INMP441 allows 0.5–3.2 MHz) | 2.856 MHz | **1.428 MHz** |
| Sample rate | 44,621 Hz | **22,311 Hz** |
| Screen span | 0–22.3 kHz | **0–11.2 kHz** |
| Hz per bar (readout step) | 43.6 | **21.8** |
| kHz labels | every 2 kHz | **every 1 kHz** (same tick positions) |
| FFTs (bar updates) per second | 43.6 | **21.8** |

One number, `MIC_BCLK_DIV` in `video_h3.v`, sets it all: the mic clock, the test tone's rate,
the readout's Hz formula, and (through `gen_h4_text.py`) the kHz axis.

## 9. Background: what "timing" is, and how it is calculated

*Written to explain the "achieves 83.3 MHz" line of the build. All numbers come from the timing
report of the build without the benchmark (commit `1d5eef6`), in
`fpga_fft/impl/pnr/fpga_fft_tr_content.html`. Each build overwrites that file: the ÷52 build of §8
gives 80.5 MHz, the same method with slightly different wires.*

### 9.1 The idea

Everything in the design moves in steps, one per clock tick. A value leaves a **register** (a
1-bit memory, a flip-flop) at one tick, passes through **logic** (LUTs) and **wires**, and must
reach the next register **before the next tick**, or that register stores a wrong value.

```
 tick n                                                                  tick n+1
   │  register A ──▶ LUT ──wire──▶ LUT ──wire──▶ ... ──▶ register B         │
   │  (launches)                                         (captures)          │
   └──────────────────────── one clock period ───────────────────────────────┘
```

| Word | Meaning | This design |
|---|---|---|
| **Clock period** | time between ticks = 1 / frequency | 74.25 MHz → **13.468 ns** |
| **Path** | one route from a register to the next | 5,947 paths checked |
| **Path delay** | how long the signal takes along it | slowest: 11.97 ns |
| **Slack** | time to spare = deadline − arrival; must be ≥ 0 | slowest: **+1.466 ns** |
| **Fmax** | the fastest clock the slowest path allows = 1 / (period − slack) | 1 / (13.468 − 1.466) ns = **83.3 MHz** |

74.25 MHz is not a choice: 720p at 60 frames/s needs 1650 × 750 × 60 = 74.25 million pixel slots
per second. So the design must pass at exactly that clock; Fmax only tells how much room is left.

### 9.2 How the tool gets the numbers (static timing analysis)

The numbers are **calculated, not measured**. After place & route, Gowin's timing analyser
(STA, *static timing analysis*) knows where every LUT and wire is. It looks up the delay of each
piece in Gowin's model of the chip and adds them up for every path. Nothing is simulated and
nothing is measured on the board.

1. **Which clocks exist.** We tell it one thing, in `fpga_fft/src/top.sdc`: the crystal on pin
   4 is 27 MHz (`create_clock -period 37.037`). The tool works out the rest from the design:
   PLL ×55 ÷ 4 → 371.25 MHz, then CLKDIV ÷5 → **74.25 MHz**. That is where "needs 74.250 MHz" comes
   from.
2. **Worst case.** For the "is it fast enough" check (*setup*), it uses the **slow corner**: the
   chip at its lowest voltage (0.95 V) and hottest (85 °C), the slowest a GW2AR-18 C8/I7 part
   may be. A path that passes there passes on every board, at any temperature in range.
3. **Every path** from each register to the next: 5,947 paths into 3,146 endpoints.
4. **Arrival vs deadline** for each: the steps below.

**Worked example: the text-table lookup** (`addr1` → `rom_text` output, slack +1.784 ns):

| Step | Delay (ns) | Total (ns) | What it is |
|---|---|---|---|
| Clock edge at the clock source | 0 | 0.000 | tick n |
| Clock travels to register A | 0.329 + 2.271 | 2.601 | the clock net reaches 956 registers, so it takes time |
| Register A puts out its value | 0.232 | 2.833 | *clock-to-Q* |
| 10 LUTs (0.37–0.56 each) | 4.345 | | logic |
| 10 wires between them (0–1.40 each) | 7.072 | | routing: **61 % of the path** |
| **Data arrives at register B** | | **14.249** | |
| Next clock edge | 13.468 | 13.468 | tick n+1 |
| Clock travels to register B | 0.329 + 2.271 | 16.069 | same clock tree, so the same delay (*skew* 0) |
| Register B needs the data this early (*setup time*) | −0.035 | **16.034** | the deadline |
| **Slack = deadline − arrival** | | **16.034 − 14.249 = +1.784** | ✅ in time |

The clock delay (2.6 ns) appears on both sides and cancels. What counts is the data path:
**11.65 ns**, against the 13.43 ns available.

**The other check, hold:** data must also not arrive **too early**, or it would overwrite what
register B is capturing at the same tick. That is checked with the **fast corner** (1.05 V,
0 °C). It almost never fails within one clock, and the build has no hold violations either.

### 9.3 What it says about the real board

- **The board is never measured.** The tool trusts Gowin's delay model, which Gowin built by
  measuring many chips, with safety margin.
- **A real chip on a desk is usually faster** than the slow corner (≈ 25 °C, ≈ 1.0 V). That is
  why a design that fails timing by a little often *seems* to work on the bench. Then it fails on
  a hot day, on another board, or once in a million frames. **Pass in STA, don't trust the bench.**
- **Measuring it on the board** is possible only roughly. Raise the clock until results go wrong
  (overclocking). Our HDMI clock must stay at exactly 74.25 MHz, so this is not useful here, and
  a scope cannot see delays inside the chip.

### 9.4 Why it improved this week (74.8 → 83.3 MHz)

| | With the benchmark | Without |
|---|---|---|
| Text-table path | 13.33 ns, slack 0.105 ns (slowest in the chip) | **11.65 ns**, slack 1.784 ns |
| Its logic | 10 LUTs | the same 10 LUTs |
| Slowest path in the chip | text table → **74.8 MHz** | inside the Gowin FFT (11.97 ns) → **83.3 MHz** |

The logic is identical, so the 1.7 ns saved is **wire**. Two reasons:
1. **More room.** The placer no longer had to fit the benchmark's ~1,500 logic cells and 8
   block RAMs around the demo, so the text table's LUTs sit closer together.
2. **No shared register.** With the benchmark in, the tool merged the text table's address
   register with the bar drawer's copy of x (to save a register). That one register fed two
   blocks in different places, so it was close to neither. Now the text table has its own.

Placement also varies from build to build: the same text path gave 79.6 MHz in one earlier build
and 74.8 MHz in the next. So 83.3 MHz is this build's result, not a promise. What changed for
good is the margin: 0.8 % → 12 %.
