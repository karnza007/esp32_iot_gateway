## 1. Idea

The advisor wants to see a **spectrogram**: many FFTs stacked over time, with colour showing
the level, so the screen shows how the sound changes rather than only how it is now.

Before building it, three questions were answered (discussion 2026-11-04):

| Question | Answer |
|---|---|
| What RAM does the design use? | Only on-chip: 12 of 46 block RAMs (18 Kbit each) and 3 small logic-built RAMs. No external memory. |
| What RAM does the 20K have? | Block SRAM (46 × 18 Kbit ≈ 100 KB), logic-built SRAM (≈ 40 Kbit), and 64 Mbit (8 MB) of SDRAM inside the GW2AR package, unused. **No PSRAM** (that is on the Tang Nano 4K and 9K). |
| Would SDRAM make the design faster or smaller? | No. On-chip RAM already gives one access per clock; SDRAM needs several clocks per access, refresh pauses and a controller (more logic). It only helps with **capacity**: a picture bigger than the free block RAM. |

**Does a spectrogram fit on-chip?** The picture must be stored, because the screen is redrawn
60 times a second:

| Picture (time × frequency × colours) | Bits | Block RAMs | Fits? |
|---|---|---|---|
| **256 × 256 × 16** (first version) | 262,144 | 16 | ✅ (34–35 free) |
| 512 × 256 × 16 | 524,288 | 32 | just |
| 1,024 × 512 × 256 | 4.2 M | — | no: needs the SDRAM |

The plan, agreed with the advisor's overlap suggestion in mind:

1. Remove the test tone from the HDMI build (this report).
2. S1 switches the display between bars and spectrogram.
3. Spectrogram 256 × 256 × 16 colours, **no overlap**: one strip per FFT, 21.8 strips/s, 45.9 ms each.
4. **50 % overlap**: each FFT uses 512 old + 512 new samples, 43.6 strips/s, 22.9 ms each. With
   no overlap, the Hann window fades each block's ends to nearly zero, so a short sound at a block
   edge is almost lost; with 50 % overlap every moment falls near the middle of some block.

## 5. Interpretation

The saving is larger than predicted because removing a source also removes everything that
chose between sources. The design now has 35 free block RAMs, enough for the 16 the first
spectrogram needs.

**Timing.** The build passes, but with 0.02 % spare instead of 14 %. The slowest path is the
dB conversion in `spectrum.v` (find the leading one, normalise, look up the log, all in one
clock), which did not change: the placer simply put it differently this time. A pass this thin
is luck, so the next build may fail. The fix is the same as on 2026-10-29: split that step over
two clocks. It should be done together with the spectrogram, which adds logic and will move the
placement again.

## 6. Problems and what they taught us

- **Timing margin can vanish without a logic change.** Removing logic changed the placement, and
  an untouched path went from comfortable to just passing. The margin belongs to a build, not to
  the design. `build.sh`'s check (achieved vs needed per clock, added 2026-10-29) reported it
  correctly.

## 8. Timing fix: the dB conversion over two clocks (2026-11-04)

**The problem (§5).** For each bin, `spectrum.v` turns the power P (32 bits) into
L = 32·log2(P) in one clock: ① find the top 1 bit (e), ② shift P so that bit lands at bit 31,
③ look up the next 5 bits in a 32-entry log table, ④ add 32·e. In the build after the tone
removal that was **19 cells in a row: 8.23 ns of logic + 5.01 ns of wires = 13.24 ns**, with
**+0.003 ns** slack. The logic was unchanged; removing the tone changed the netlist, the placer
laid the design out again, and these cells ended up further apart (in the 85.0 MHz build of
2026-10-29 the same path was at most about 11.5 ns, so the change was about 1.7 ns of wire).

**The fix.** A register between ② and ③: stage 4a keeps e and the 5 bits below the top bit
(10 bits), stage 4b does the table and the add. The valid, address and zero flags, and
`bar_done`, get one more stage, so the bars arrive one clock (13.5 ns) later.

| Check | Result |
|---|---|
| Bar heights, old vs new `spectrum.v` (sweeping tone + 1 kHz, 4 FFT blocks, Gowin FFT model) | **all 2,048 writes identical**, every one exactly 1 clock later |
| `tb_h4_peak`, fixed 3 kHz / sweep | PASS 6/6 / PASS 6/6 |
| Build | **2,278 logic (11 %), 775 registers, 11 / 46 block RAMs, 6.5 / 24 DSP; 89.0 MHz** (20 % spare) |
| Slowest path now | inside the Gowin FFT core (butterfly multiplier → its RAM), slack +2.23 ns |

Logic went up by 71 cells for about 15 new registers; the rest is the tool packing logic
differently, as usual between builds. The best timing of the demo so far.

## 10. Step 3: the spectrogram (2026-11-04)

**Idea.** Every FFT already produces 512 bar heights for the bars screen. The spectrogram keeps
them: each FFT becomes one column of a picture, colour = level, and the screen shows the latest
256 columns.

```
spectrum.v ── 512 heights per FFT ──┬─▶ bar_display         (bars, unchanged)
                                    ├─▶ peak_readout        (unchanged)
                                    └─▶ spectrogram_display (new)
                                          ① bin pair 2r, 2r+1 → row r: the louder of the two
                                          ② height → colour number: height / 37.5 (5 dB, 0..15)
                                          ③ one column of the 256 × 256 × 4-bit memory
                                          ④ screen: start column + (x − 128) / 4, row (659 − y) / 2
```

| Design choice | Value | Why |
|---|---|---|
| Picture | 256 columns × 256 rows × 4 bits = 262,144 bits | fits in **16 block RAMs** on-chip (no SDRAM) |
| On screen | x 128–1151, y 148–659; each point 4 × 2 px | 1,024 × 512 px; same bottom edge as the bars screen |
| History | 256 FFTs × 45.9 ms = **11.7 s**, newest at the right | layout A, chosen 2026-11-04 |
| Joining bins | the louder of each pair (43.6 Hz per row) | a narrow tone keeps its full brightness |
| Colours | 16, 5 dB each; 0 = black (−80 to −75 dB), then matplotlib's "inferno" | black hides the FFT rounding grass at about −80 dB |
| Scrolling | only the start column moves, in vertical blanking | the picture never tears; screen column 0 (being overwritten) is drawn black |
| Labels | kHz every 1 kHz (left), −10 s … now every 2 s (bottom), colour scale 0/−40/−80 dB (right) | text page 1 + `rom_spec.v`, both from `gen_h4_text.py`; 4 lowercase glyphs (n, o, s, w) added to the font |

## 11. Step 4: 50 % overlap (2026-11-04)

**Idea.** Each FFT multiplies its 1,024 samples by the Hann window, which fades the block's
start and end to nearly zero. Without overlap, a short sound (a clap, a click) that lands near
a block edge is almost lost. With 50 % overlap a new FFT starts every 512 samples on the latest
1,024, so every moment is near the middle of some block, and there are twice as many columns.

**The design change (`spectrum.v`).** Until now the window was applied as samples were stored,
into two halves of 1,024. With overlap each sample is used twice, at two different window
positions, so that no longer works:

| | Before | Now |
|---|---|---|
| Buffer | 2 halves of 1,024 **windowed** samples | ring of 2,048 **raw** samples (same memory) |
| Window | multiplied when storing | multiplied as the FFT reads (same multiplier, moved) |
| FFT start | every 1,024 samples | every 512 (`OVERLAP = 1`), or every 1,024 (`OVERLAP = 0`) |
| Columns | 21.8 / s, 45.9 ms each | **43.6 / s, 22.9 ms each** |
| Screen history | 256 columns = 11.7 s | 256 columns = **5.9 s** (option A, chosen 2026-11-04); time labels −5 s … now, every 1 s |

`OVERLAP = 0` keeps the old behaviour for the H2 design and for comparisons; the HDMI demo uses 1.

**Hypothesis.** *If the window moves to the read side, `OVERLAP = 0` gives bar heights identical
to the old design, and `OVERLAP = 1` gives an FFT every 512 samples whose every second block is
identical to the old one, because those blocks hold exactly the same 1,024 samples and the same
arithmetic (sample × window / 32768) is done, only at a different time.*

**Results.**

| Check | Result |
|---|---|
| `OVERLAP = 0` vs the committed design (sweeping tone + 1 kHz, Gowin FFT model, 4 FFTs) | all bar heights **identical, on the same clock** |
| `OVERLAP = 1` vs the committed design (7 FFTs) | FFTs 0, 2, 4, 6 **identical** to the old 0, 1, 2, 3; FFTs 1, 3, 5 new (each differs from both neighbours); FFTs **8,192 clocks apart** instead of 16,384 |
| `tb_h4_peak`, fixed 3 kHz / sweep (now with overlap; the sweep's block range starts two `block_ready`s back) | PASS 6/6 / PASS 6/6, no overrun |
| `tb_h5_chain` (sweep through the real chain) | PASS: line at **1.50 rows per column** (half of before: twice the columns); 1 kHz tone colour 4; 100 % dark elsewhere |
| `tb_h5_spec` (spectrogram page) | PASS; time axis reads "-5s -4s -3s -2s -1s now" |
| `tb_h4_frame` (bars page) | PASS, pixel-identical |
| Build | **2,645 logic (13 %), 922 registers, 27 / 46 block RAMs, 7 / 24 DSP; 75.5 MHz** |
| Board | uploaded; checked on the monitor by hand (no capture card) |

**Timing note.** 75.5 MHz passes with only 1.6 % spare. The slowest path is not the new read
path but the old text-ROM lookup (`rom_text`, built from logic, one clock), which grew when it
got a second page in step 2: x → 11 cells → the ROM output register. The same path was the

a block RAM (19 are free).

## 12. Timing fix: the text table in block RAM (2026-11-04)

**The problem (§11).** The screen-text table (`rom_text`: which character, in which colour, in
each 16 × 16 cell) was built from logic: 278 entries, a 14-bit address, **400 logic cells, 11
deep**, 13.25 ns of a 13.47 ns clock. The first plan, "give it a second clock", would not have
helped: the table already had a clock to itself, and a lookup has no natural middle to put a
register in (unlike the dB maths in §8, which was a chain of separate steps). Splitting it
would have meant rebuilding it as a two-level table.

**The fix.** Store it in block RAM, like the font already was. A block RAM answers any address
in one clock with a short, fixed delay, so the delay through the screen pipeline is unchanged.
To keep it small the table was made compact:

| | Before | After |
|---|---|---|
| Address | {page, row, column}: 2 × 64 × 128 slots | page × 3,600 + row × 80 + column: 7,200 slots (row × 80 computed in the address clock) |
| Word | 10 bits: colour, live flag, ASCII | 9 bits: colour, ASCII; codes 0–15 = live character (unused control codes) |
| Built from | 400 logic cells | block RAM (`syn_romstyle = "block_rom"`) |

| Check | Result |
|---|---|
| Bars page frame | **pixel-identical** to before the change |
| Spectrogram page frame | **pixel-identical** to before the change |
| Build | **2,297 logic (12 %, −348), 921 registers, 32 / 46 block RAMs (+5), 7 / 24 DSP; 81.9 MHz** (10 % spare) |
| Slowest paths | all inside the Gowin FFT core (slack +1.25 ns); the text path is gone |
| Board | uploaded; checked on the monitor by hand |

The tool used 5 block RAMs, one more than the 4 estimated (7,200 × 9 bits fits 4 blocks of
2,048 × 9; how the tool split it was not investigated).
