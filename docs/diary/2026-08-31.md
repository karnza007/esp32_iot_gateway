# 2026-08-31

## Null test PASSED on hardware

M2 bitstream programmed. Ran 191 s continuous at `BCLK_DIV = 25`:

```
30 frames/s, 0 lost, 0 overflow, 0 checksum errors, verdict OK
```

Every second, for three minutes, all zeros. The instrumentation adds no loss of its own.
Baseline recorded: `data/run-n25-null-v1metrics.csv`.

## Two flaws the real data exposed that simulation could not

**1. `resyncs` was measuring nothing.** The CSV showed `resyncs` exactly equal to
`frames_ok` — 30 and 30, every single second. The reader calls `_resync()` once per frame
by construction, so the counter incremented on every frame whether or not anything had gone
wrong. It looked like a health metric and was actually a frame counter in disguise.

Fixed: `_resync()` now returns how many bytes it had to discard before finding the sync
word. In a healthy stream that is 0 every time, because the sync sits immediately after the
previous frame. The stats now carry `resync_events` (times the stream had to be re-found)
and `bytes_skipped` (how much garbage was scanned). Both read 0 in a healthy link, which is
what a health metric should do.

**2. The throughput number was ambiguous.** I had predicted ~30.35 kB/s; the CSV read
~30.03 kB/s and I briefly thought the bitstream was stale. Neither was wrong — they are
different quantities:

| | at 15 kHz |
|---|---|
| payload (audio bytes delivered) | 29.30 x 1024 = **30,000 B/s** |
| wire (payload + framing) | 29.30 x 1036 = **30,352 B/s** |

The viewer was reporting payload and I was quoting wire. Both are now reported and logged
separately as `payload_Bps` and `wire_Bps`. This matters beyond tidiness: `wire_Bps` is the
one to compare against the UART's 200 kB/s capacity, so the whole M3 saturation analysis
depends on not confusing them. It also means the "is the new bitstream running?" check must
use `wire_Bps` (30,352 vs M1's 30,120) — `payload_Bps` is 30,000 in both versions.

## A design decision reversed: the overflow counter now wraps

The overflow counter saturated at `0xFFFF`. I had justified that as "a pegged counter
unambiguously means massively overflowing". Working through the M3 numbers showed it is
simply wrong.

Once pegged, the per-interval **delta reads zero**. The host's verdict logic keys off the
delta, so at the exact moment the FPGA is overflowing hardest, the verdict would flip from
`LINK SATURATED (FPGA FIFO)` to `GATEWAY LOSS (ESP32/USB)` — blaming the wrong component,
which is the one question this whole project exists to answer. And it is not theoretical:
at M3 rates the counter pegs within seconds.

Now free-running. The host rebuilds the true total by summing modulo-65536 differences
between consecutive frames. That stays exact as long as fewer than 65536 bytes are dropped
between two *received* frames — about 1.9 MB/s of loss at 29 frames/s, an order of
magnitude beyond what a 200 kB/s link can offer. Unreachable in this system.

## Positive control retuned

Originally planned `CLK_PER_BIT = 48`. Checked the arithmetic: that is 500 kbaud =
50 kB/s against a 30.35 kB/s demand — only 61 % loaded, so it would **not** have
overflowed at all, and the test would have "failed" while everything was working.

Need baud/10 < 30,352, so `CLK_PER_BIT > 79`. Using **`CLK_PER_BIT = 96`** → exactly
250,000 baud → 25 kB/s against 30.35 kB/s demand. Deficit ≈ 5.4 kB/s, unambiguous overflow.
